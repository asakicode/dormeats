# 메뉴 묶음(같은 음식 다른 이름) 설계

## 왜 하는가

즐겨찾기 탭은 하트 누른 메뉴의 "다음 등장"을 보여주는 게 핵심 기능이다. 그런데 영양사가 같은 음식을 매번 조금씩 다른 이름으로 올린다(미역냉국 ↔ 미역오이냉국, 참치김치찌개 ↔ 돈김치찌개, 씨리얼 ↔ 씨러얼). 지금은 이름이 정확히 같아야만 매칭되어서, 메뉴 이름 622개 중 360개(58%)가 한 번만 나온 이름이고 하트를 눌러도 다음 등장이 거의 뜨지 않는다.

목표: 미역냉국에 하트를 누르면 "다음 등장: 미역오이냉국 · 10/30(금) 점심"이 뜬다.

## 목표 / 비목표 / 안티골

**목표**
- 같은 음식으로 볼 메뉴 이름들을 "묶음"으로 관리한다.
- 즐겨찾기 다음 등장, 홈 하트 표시가 묶음 단위로 동작한다.
- 운영비 0원.

**비목표**
- 관리자 화면(묶음은 저장소의 파일로 관리).
- 도봉학사 외 다른 기숙사.
- 푸시 알림.

**안티골 (이렇게 되면 실패)**
- 글자 유사도만으로 자동 묶기 → 삼치카레구이와 갈치카레구이, 돈낙지불고기와 돈가지불고기가 섞인다. 금지.
- 유료 AI API, 로컬 LLM 사용. 금지.
- 다른 음식이 하트 채워진 채로 보이는 것.

## 발견한 기존 버그 (이번 범위에 포함)

`scripts/crawl-menu.ts`의 `findMatchingMenuItem`은 이름이 서로 포함되면(부분 문자열) 같은 `menu_items`로 매칭하고, 새 이름이 더 길면 기존 행 이름을 덮어쓴다("메뉴명 보강"). 2026-10-19 주 사이트 원본과 DB를 비교한 결과 실제로 틀린 이름이 저장되어 있다.

| 사이트 원본 | DB에 저장된 이름 |
|---|---|
| 바나나 | 바나나우유 |
| 사과 | 사과즙 |
| 김치전 | 오징어김치전 |
| 치즈계란말이 | 청양치즈계란말이 |
| 호박된장국 | 애호박된장국 |
| 김치비지찌개 | 돈김치비지찌개 |

즉 홈 화면에 실제와 다른 메뉴 이름이 보이고 있다. 이 부분 매칭이 바로 안티골의 "글자 기준 자동 묶기"이므로 없앤다.

- `menu_items`는 공백만 정규화한 **정확한 이름**으로만 매칭한다. 부분 매칭과 이름 덮어쓰기는 삭제.
- 지난 주(2026-07-13 주부터 현재 주까지)를 다시 크롤링해 `meal_items`를 올바른 이름으로 다시 연결한다. 크롤러가 특정 주를 인자로 받을 수 있게 한다. 다시 크롤링해도 `meals`는 upsert, `meal_items`는 삭제 후 재삽입이라 기존 구조 그대로 동작한다.
- 재크롤링 후 어떤 식단에도 연결되지 않는 잘못된 `menu_items` 행(예: 바나나우유)은 지우지 않고 남겨 둔다(즐겨찾기가 참조하고 있을 수 있음).
- 기존 즐겨찾기는 옮기지 않는다. (Claude 결정) 이름이 덮어쓰인 행(id는 그대로, 이름만 "바나나" → "바나나우유")을 하트한 즐겨찾기는 그 행의 현재 이름을 따라간다. 원래 무엇을 의도했는지 알 방법이 없고, 영향받는 건 덮어쓰기가 일어난 소수 행뿐이다. 재크롤링 전에 덮어쓰인 행을 참조하는 즐겨찾기 개수만 세어서 사용자에게 알린다(누가 했는지는 출력하지 않음).
- 묶음표는 재크롤링이 끝난 뒤의 이름을 기준으로 만든다.
- 크롤러 인자 (Claude 결정): 인자가 없으면 지금처럼 이번 주만 크롤링한다(매일 cron은 그대로). `--from YYYY-MM-DD`를 주면 그 날짜가 속한 주부터 이번 주까지 한 주씩 크롤링한다. 정확 매칭 수정만으로는 매일 cron이 데이터를 망가뜨리지 않는다.
- 운영 DB에 쓰는 실행(재크롤링, 묶음 반영)은 Claude가 실행 전에 사용자에게 확인을 받는다. 스키마 SQL은 사용자가 Supabase SQL 편집기에서 직접 실행한다.

## 묶는 기준 (사용자와 확정)

- **음식 종류가 중심인 메뉴는 하나로 묶는다**: 김치찌개(참치/스팸/돈/돈삼겹/햄), 김치볶음밥(스팸/참치), 미역냉국(미역냉국/미역오이냉국), 계란말이(청양/청양치즈/부추), 부추전(새우/새우살/해물).
- **생선은 생선별로 묶고, 조리법·양념 차이는 무시한다**: 삼치구이·삼치카레구이·삼치조림·삼치감자조림·삼치데리조림은 모두 "삼치". 갈치, 고등어, 임연수는 각각 따로.
- **불고기는 고기별로 묶는다**: 소 / 돼지 / 오징어 / 오리. 돈낙지불고기처럼 섞인 것은 주재료로 판단한다.
- **국수는 종류별로 따로 둔다**: 잔치국수, 콩국수, 칼국수, 쌀국수, 냉메밀국수는 각각 다른 메뉴. 미니콩국수 ↔ 미니냉콩국수처럼 거의 같은 것만 묶는다.
- **오타·줄임말·곁들임 소스 차이는 같은 메뉴**: 씨러얼→씨리얼, 캐마일/카모마일→캐모마일, 메알→메추리알, `&양념다대기` ↔ `&다대기`, `*라면사리` ↔ `&라면사리`.
- **메뉴가 아닌 문구**("즐거운 추석 명절 보내세요" 등)는 어느 묶음에도 넣지 않는다.
- 기준에 딱 맞지 않는 애매한 경우는 Claude가 위 기준의 취지대로 판단하고, 묶음표를 사용자에게 한 번 보여준 뒤 확정한다.

## 동작 (사용자와 확정)

**홈 식단 화면**
- 하트 누른 메뉴와 같은 묶음인 메뉴는 하트가 채워져 보인다.
- 채워진 하트를 누르면 그 묶음의 즐겨찾기가 전부 해제된다. (사용자 확인함)

**즐겨찾기 탭**
- 하트 누른 이름을 보여주고, 그 아래에 실제로 나올 이름과 날짜를 보여준다. 예: `미역냉국` / `다음 등장: 미역오이냉국 · 10/30(금) 점심`.
- 같은 묶음에 즐겨찾기가 여러 개 있어도 한 줄만 보인다. (사용자 확인함)
- 줄의 하트를 끄면 그 묶음의 즐겨찾기가 전부 해제되고, 실행취소하면 해제된 것이 전부 복구된다(지우기 전에 지울 행들의 `menu_item_id`를 기억해 두었다가 다시 넣는다).
- 하트를 켤 때는 누른 메뉴 한 행만 `favorites`에 넣는다. 묶음 전체로 퍼뜨리지 않는다. (Claude 결정)
- `favorites`에 `(user_id, menu_item_id)` 유니크 제약이 없으면 스키마 SQL에서 함께 추가한다(빠른 연타나 실행취소로 중복 행이 생기는 것 방지). 추가 전에 기존 중복 행이 있는지 확인한다.

**새 이름 처리**
1. 크롤링할 때 새 이름이 나오면 규칙으로 "메뉴 키"를 만든다(공백 제거, 오타 사전 적용, `&`·`*` 뒤 곁들임 제거). 이 키가 이미 묶음에 속한 이름의 키와 같으면 그 묶음에 자동으로 넣는다.
2. 규칙으로도 안 맞는 이름은 묶음 없이(혼자) 둔다. 혼자인 메뉴는 지금처럼 자기 이름으로만 매칭된다.
3. 한 달에 한 번쯤 사용자가 Claude Code에서 "새 메뉴 묶어줘"라고 하면, 묶이지 않은 이름 목록을 뽑아 Claude가 묶음 파일에 추가하고 반영 스크립트를 실행한다.
4. 사용자가 3번을 할 때를 알 수 있도록, 매일 크롤링이 끝나면 GitHub Actions 결과 화면(job summary, `$GITHUB_STEP_SUMMARY`)에 "묶이지 않은 메뉴 N개 (이번 실행에서 새로 생긴 이름: …)"를 적는다. 사용자가 이 정도 알림이면 충분하다고 확인함. 다른 알림 수단은 만들지 않는다.

## 나중에 할 것 (이번 범위 아님)

- 데이터가 많이 쌓이면 자동 분류를 붙이고 싶다(사용자 희망). `data/menu-groups.json`이 "이름 → 묶음" 정답 데이터 역할을 하므로, 나중에 여기서 무료 규칙(예: 특정 재료 단어가 들어간 이름은 항상 같은 묶음이었다)을 뽑아 새 이름에 적용할 수 있다. 이를 위해 JSON 형식은 단순한 `{ 묶음 이름: [메뉴 이름...] }`으로 유지하고, 묶음 이름은 사람이 읽을 수 있는 음식 이름(예: "김치찌개", "삼치")으로 짓는다.

## 구조

**DB** (Claude 결정)
- 새 테이블 `menu_groups (id uuid pk, name text unique not null, created_at)`.
- `menu_items`에 `group_id uuid null references menu_groups(id) on delete set null` 추가.
- RLS: `menu_groups`는 `menu_items`와 같은 패턴(anon/authenticated 전체 조회, 쓰기는 service_role만). `supabase/rls_policies.sql`에 추가.
- 스키마 변경 SQL은 Supabase SQL 편집기에서 사용자가 직접 실행한다(저장소에 마이그레이션 도구가 없음). SQL 파일을 `supabase/` 아래에 둔다.

**묶음표 원본** (Claude 결정)
- 저장소 파일 `data/menu-groups.json`이 기준이다: `{ "묶음 이름": ["메뉴 이름", ...] }`. git으로 변경 이력을 볼 수 있고 Claude Code가 편집하기 쉽다.
- `scripts/apply-menu-groups.ts`: JSON을 읽어 `menu_groups`를 upsert하고, 이름이 일치하는 `menu_items.group_id`를 설정한다. 여러 번 실행해도 결과가 같아야 한다. JSON에 있는데 DB에 없는 이름은 경고만 출력한다.
  - JSON에 적힌 이름은 JSON이 정답이다(다른 묶음으로 옮기면 DB도 옮겨짐). JSON에 없는 이름은 건드리지 않는다. 크롤러가 자동으로 묶은 이름이 JSON에 없어서 풀리는 일을 막기 위해서다. (Claude 결정)
  - 묶음은 이름으로 식별한다. 묶음 이름 바꾸기는 지원하지 않는다(새 이름으로 옮기면 새 묶음이 생김). 멤버가 하나도 없는 묶음은 스크립트가 지운다.
- `scripts/list-ungrouped-menus.ts`: `group_id`가 없는 메뉴 이름과 등장 횟수, 그리고 크롤러가 자동으로 묶었지만 JSON에는 아직 없는 이름을 출력한다. 월 1회 작업 때 후자도 JSON에 옮겨 적어 JSON을 완전하게 유지한다.
- 두 스크립트 모두 기존 스크립트처럼 `.env.local`을 dotenv로 읽고, 비밀값은 출력하지 않는다.

**규칙 함수** (Claude 결정)
- `lib/menu-group.ts`에 순수 함수로 둔다: `menuKey(name)`(오타 사전·곁들임 제거), `groupKeyOf(item)`(`group_id`가 있으면 그것, 없으면 `item:<menu_item_id>`), 다음 등장 계산. `lib/meal-time.test.ts`처럼 `tsx --test`로 테스트한다.
- 크롤러는 새 `menu_items`를 만들 때 `menuKey`가 같은 기존 묶음 멤버를 찾아 `group_id`를 같이 넣는다.

**화면**
- `app/favorites/page.tsx`: 즐겨찾기와 다가오는 식단을 `group_id`까지 조회하고, 다음 등장을 묶음 키 기준으로 계산하며 실제 이름도 함께 저장한다. 같은 묶음 즐겨찾기는 한 줄로 합친다.
- `app/components/FavoriteButton.tsx`: 묶음 기준으로 채움 여부를 판단하고, 해제 시 묶음 전체를 지운다. 홈(`MealSection`)과 즐겨찾기 탭이 함께 쓴다.
- `app/mypage/page.tsx`의 즐겨찾기 목록도 같은 묶음은 한 줄로 합친다. (Claude 결정)

## 작업 순서

1. 크롤러 정확 매칭으로 수정, `--from` 인자 추가, 지난 주 재크롤링.
2. DB 스키마(`menu_groups`, `group_id`, 필요하면 favorites 유니크 제약) 추가. 크롤러가 `group_id`를 쓰는 코드(4단계)보다 반드시 먼저 적용한다.
3. Claude가 재크롤링된 이름 전체로 `data/menu-groups.json` 초안 작성 → **사용자 검토 후 확정** → 반영 스크립트 실행. 검토는 멤버가 2개 이상인 묶음만 목록으로 보여준다(혼자인 이름은 생략). 검토를 기다리는 동안 4·5단계 코드는 작은 임시 JSON으로 먼저 진행해도 된다.
4. 규칙 함수, 크롤러 자동 묶기.
5. 즐겨찾기 탭, 하트 버튼, 마이페이지 수정. `FavoriteButton`의 props(`groupId` 추가 등)와 호출부, 홈 식단 조회에서 `group_id`를 같이 가져오는 변경은 자유롭게 해도 된다.

## 구현하는 사람에게 맡기는 것

- 묶음 기준 즐겨찾기 조회 방식(임베드 `!inner` 필터 또는 멤버 id 목록으로 두 번 조회).
- 같은 화면에 같은 묶음 메뉴가 두 개 동시에 보일 때 한쪽 하트를 바꾸면 다른 쪽도 즉시 바뀌게 할지(드문 경우라 새로고침 후 맞으면 충분, 쉽게 되면 맞춰도 됨).
- 오타 사전의 정확한 항목은 재크롤링 후 이름을 보고 채운다.
- 지난 주 사이트 페이지가 7월 주까지 열리는지 확인하고, 안 열리는 주는 그대로 둔다.
